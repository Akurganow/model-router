## Objective

model-router routes each subagent spawn to a model and an effort, chosen from TypeSafe Jev's judgment of the task. Today it does this in Claude Code. This heist extends it to Oh My Pi (omp) and, behind gate G1, to Codex CLI. All of it ships from the same repository in one release.

All harnesses share one pure routing core. Each harness gets its own binding, setup interview, escalation instructions and documentation.

Success means parity with Claude Code: each shipped harness routes model and effort on every eligible spawn and writes one decision line per routed call. Savings are not measured in this heist.

Wherever this contract says "the shipped plugins", it means Claude Code, omp and, if G1 passes, Codex.

## Gates

**G1, the Codex probe.** The Don runs `docs/gangsta/multi-harness/recon/codex-probe-prompt.md` (revision 3) and returns its report. G1 is judged separately for each multi-agent version (v1 and v2) used by a visible Codex model. A version passes when its runs show all four of these:
- the spawn reaches the hook under the anchored matcher;
- the hook receives `message` as readable task text (`messageIsTask` true);
- the rewritten model and effort are the ones the child actually runs on, per the session files;
- the parent run completes.

G1 also records whether the decision line (FR-035) is visible in the interactive CLI or in `codex exec` output. If it is visible in neither, Codex still ships: the Codex README says the line is not shown, the coverage issue (AC-10) records it, and the Objective's line requirement is waived for Codex only.

Codex ships if at least one version passes. The hook then matches only the tool names of the passing versions, and a spawn from a failing version is never sent to Jev. If no version passes, Codex is deferred (see "If G1 fails").

Probe items that only the human steps answer, such as trust prompts, `.env` reach and the desktop app, are recorded as "not verified" when skipped. They do not decide G1.

**G2, calibration.** After FR-004, `node scripts/calibrate.ts` against `jev-latest` reports tier and work agreement of 85% or more. The resolved Jev model is recorded with the figures. A miss is fixed by rewording, never by lowering the bar (README, Development).

**G3, regression proof.** The constitution's regression proof passes: `npm ci`, `npm run check`, `claude plugin test plugins/model-router`.

## Requirements

### Functional Requirements

**Shared core** (source folder `shared/`)

1. FR-001 `shared/core.ts` holds the calibrated data and the routing logic:
   - the tier texts, the work texts, the question instructions, `TIE_MARGIN`, `WORK_PRIOR` and `BUDGET_CHARS`;
   - preparing the brief (FR-004);
   - the Jev request body;
   - answer parsing, and tier and work picking;
   - the transport error type and the retry rule (FR-005);
   - the decision-line suffix (FR-006).

   It uses no network, no process environment and no timers. The caller passes in the HTTP call and the wait.
2. FR-002 The core returns a tier index, a work index and both probability sets, or a skip reason. It names no model and no effort.
3. FR-003 The core accepts the list of tier texts from its caller.
   - The answer parser accepts exactly one probability per offered tier, and anything else is a malformed answer.
   - The best tier wins. A higher tier wins instead when its probability is strictly less than `TIE_MARGIN` below the best, checked from the top tier down.
   - With three tiers the results equal today's.
   - Any tier count other than three is built only if G1 passes.
4. FR-004 Preparing a brief:
   1. Redact secrets in the full text.
   2. Replace code blocks with their size notes and collapse blank lines.
   3. If the result is longer than `BUDGET_CHARS` (12000), keep the head and the tail and join them with a fixed omission marker. The marker counts toward the budget. The head gets two thirds of the remaining characters, rounded down, and the tail gets the rest. The total equals the budget.

   The omp context (FR-024) goes through the same steps on its own.
5. FR-005 The transport error type has three classes: network, timeout and HTTP status.
   - A network error, or HTTP status 408, 429 or 5xx, is retried once after 300 ms, through the wait the caller passed in.
   - A timeout, any other status and any plain error are not retried.
   - The retry stays inside the caller's single 8 s deadline.
   - These skip texts stay exactly as today: "HTTP <status>", "no answer in 8000 ms", "api_key unset", "malformed answer". A network error reads "network error".
6. FR-006 The decision-line suffix appends " · jev <model>" and " · <input>/<output> tok" when the Jev response carries those fields. The model part is left out when the response has no model. The token part appears only when both counts are present. The model string keeps only letters, digits, dot, dash and underscore, and at most 40 characters.

   Example: "L1 sonnet · medium · p=0.80/0.60 · jev jev-1.14.0 · 812/9 tok". The prefix stays as each binding writes it today.
7. FR-007 `shared/jev.ts` builds and sends the TypeSafe request:
   - the fixed endpoint;
   - the bearer key;
   - the abort signal;
   - the core's typed error on failure.

   omp and Codex use it. The Claude Code folder does not contain it, and keeps its network call in its registration module.
8. FR-008 The endpoint is fixed at `https://api.typesafe.ai/v1/systemone` in every harness. No variable or setting redirects it, `TYPESAFE_BASE_URL` included.
9. FR-009 `scripts/sync.ts` copies the files from `shared/` byte-identically into each plugin folder that uses them. Its check mode fails on any difference and on unequal plugin versions (FR-051).

**Claude Code**

10. FR-010 The Claude Code plugin keeps its folder, manifest, catalog entry and hook declaration. `tools/surface.json` stays unchanged.
11. FR-011 `hooks/router.ts` becomes an adapter on the core. It keeps its public exports and the exact shape of its decision object. The model map (`haiku`, `sonnet`, `opus`) and the effort ladder stay in the adapter.
12. FR-012 `hooks/register.ts` changes in three ways:

    - key order and debug logging.
13. FR-013 The Claude Code test suite changes only in two places:
    - the three expected decision-line strings (FR-006);
    - one clock advance and a second expected request in the HTTP 529 test (FR-005).
14. FR-014 The Claude Code documents state the new behaviour:

**Oh My Pi** (folder `plugins/model-router-omp`)

15. FR-020 The omp plugin folder holds:
    - a `package.json` with `omp.extensions`;
    - three agent definitions;
    - the extension, and copies of `shared/core.ts` and `shared/jev.ts`;
    - a setup skill and an escalation skill;
    - tests;
    - a README, a PRIVACY.md and a LICENSE (MIT, as the repository).

    The README states that the extension reads the `task.md` files of FR-026 and the variables of NFR-003.

    It has no `.claude-plugin` manifest, so omp keeps the agents' `model` field (dossier, Oh My Pi, Models and roles).
16. FR-021 The three agents are `router_light`, `router_mid` and `router_heavy`.
    - Each copies the body, tools and spawn policy of omp's bundled `task` agent at v18.2.8.
    - Each carries an attribution line naming omp, its MIT licence and that version. The licence is in omp's `LICENSE` and `packages/coding-agent/package.json:17` at v18.2.8.
    - Each runs at thinking level `auto`.
    - The model selector is the agent's own role first, then a fallback: light falls back to smol, mid to task, heavy to slow. The bundled `task` agent runs on the task role (omp `packages/coding-agent/src/task/agents.ts:54` at v18.2.8).
17. FR-022 The extension handles `tool_call` for the `task` tool only. It routes only batch items whose `agent` is absent or `task` and whose `task` is a non-empty string. Every other item is left untouched. A call without a `tasks` list, or with an empty one, is left untouched.
18. FR-023 For each routed item the extension sets two fields, and never overwrites an `effort` the caller set:
    - `agent` becomes the tier's router agent;
    - `effort` comes from the work level. Mid and heavy map to `lo`, `med`, `hi`. Light maps to `med`, `med`, `hi`, because a small model at its lowest level stops early (`docs/model-choice.md`).

    At most four items are scored at once.
19. FR-024 The scored brief is the item's task, prepared alone, then the batch context, prepared alone by FR-004 with the cap as its budget. The cap is the smaller of the budget left over and 3000 characters. The context is dropped when fewer than 500 characters remain. The task is never cut to make room for the context.
20. FR-025 The extension shows one notification per batch: one line, with one entry per item joined by " | ". Without a UI it writes the same line to standard error. Each entry is the decision line or the skip reason, prefixed with the item's position.
21. FR-026 The extension leaves a batch unrouted, and the batch line says why, in two cases:
    - a `task.md` exists in the user agent folder or in the nearest project agent folder. Those are the agent discovery paths in omp's `task/discovery.ts`.
    - no TypeSafe key is found.
22. FR-027 The extension never throws and never blocks a spawn. On any failure, including an abort, the item keeps its original agent, and its entry names the skip reason.
23. FR-028 The extension reads two values:
    - the key, from omp's own TypeSafe credential and then from `TYPESAFE_API_KEY`;
    - the Jev alias, from `MODEL_ROUTER_JEV`, where `jev-preview` selects the preview and anything else selects `jev-latest`. The interview stores it in omp's agent `.env` file, which omp loads at start (omp `packages/utils/src/env.ts:290`), so it survives GUI launches.
24. FR-029 The setup interview asks one question at a time and writes nothing without consent. It:
    1. checks that a key exists, using omp's own status or the environment variable, without printing it;
    2. detects whether omp's auto thinking runs for spawns. With the user's consent, because it spends model usage, it spawns one `task` and reads that session for an auto-thinking usage record;
    3. explains both effort modes and asks which one decides;
    4. lists the user's models and proposes one per role;
    5. warns when all three roles resolve to one model, because routing then changes only effort;
    6. writes the router roles into the store that `modelRoleStorage` names, merged with the existing roles;
    7. in router-effort mode, sets `task.enableEffort` to true and `task.maxEffort` to high, always together;
    8. asks for the Jev alias and writes `MODEL_ROUTER_JEV` to omp's agent `.env` file;
    9. warns, and does not enable routing, where a custom `task` agent or `task.disabledAgents` would defeat it;
    10. ends with a smoke test: one spawn shows its batch line and runs at an effort no higher than high.

**Codex** (folder `plugins/model-router-codex`; built only if G1 passes)

25. FR-030 The Codex plugin folder holds:
    - a Codex manifest;
    - one PreToolUse hook entry, with a 15 s timeout;
    - the hook script, and copies of `shared/core.ts` and `shared/jev.ts`;
    - a setup skill and an escalation skill;
    - tests with the probe payload as a fixture;
    - a README, a PRIVACY.md and a LICENSE (MIT).
26. FR-031 The hook matches the tool names of the passing G1 versions, anchored at both ends. The script checks the name again.
27. FR-032 The hook command is one fixed string. It runs the script with Node 22.18 or later when present, and with Bun otherwise. No variable selects the program. On Windows the hook runs a command that does nothing and exits successfully.
28. FR-033 The hook passes the call through unchanged, with no output, for any of these:
    - any other tool name;
    - a fork. In v1 that means `fork_context` true. In v2 it means `fork_turns` absent, because Codex's default is "all", or any value other than "none". This is interim, until the fork policy is decided (Unresolved Objections).
    - a caller-set `model`;
    - a requested role. That means `agent_type` in the call's arguments, absent or `default`; the envelope field of the same name, set on nested spawns, does not count.
    - a `message` that is not a non-empty string. The matcher already limits routing to tool names of versions that passed G1 (FR-031).

    A nested spawn, whose envelope carries `agent_id`, is routed like any other spawn if probe run B7 shows the hook fires for it with a readable `message`. Otherwise nested spawns pass through.
29. FR-034 Codex has two tiers, Luna and Sol, and the Luna and Sol slugs are constants in the hook script, taken from the G1 report.
    - Luna's text merges Claude's tiers 0 and 1. Sol's text derives from tier 2.
    - The effort ladders are Luna medium, high, xhigh and Sol low, medium, high.
    - The texts and the ladders are marked provisional, except where a source supports them: OpenAI's guidance to start Luna at high.
    - Routing never assigns GPT-6 Astra.
30. FR-035 A routed call returns three things:
    - `allow`;
    - the original arguments with the chosen model and, unless the caller set one, the effort, with every other field, `message` included, copied verbatim;
    - the decision line as a system message.

    Whether `allow` changes an approval prompt or a deny rule for the spawn is not verified. The READMEs make no claim about it until a run settles it.
31. FR-036 A skip caused by Jev or the transport returns the skip reason as a system message. A deliberate pass-through returns nothing. Any exception exits successfully with no output.
32. FR-037 The hook reads two values:
    - the key, from `TYPESAFE_API_KEY` in the Codex process environment, which includes `~/.codex/.env`;
    - the Jev alias, from `MODEL_ROUTER_JEV`, as in FR-028.
33. FR-038 The setup interview asks one question at a time and writes nothing without consent. It:
    1. finds the runtime;
    2. checks that a key exists without printing it, and tells the user to add the key to `~/.codex/.env` themselves;
    3. confirms that the Luna and Sol slugs appear in `codex debug models` with every ladder level. If either is missing, it says routing would cause tool errors on this account and leaves the plugin disabled.
    4. asks for the Jev alias and writes `MODEL_ROUTER_JEV` to `~/.codex/.env`;
    5. offers to exclude `TYPESAFE_API_KEY` from agent shells in `~/.codex/config.toml`, merged with any existing exclusion and shown as a diff;
    6. tells the user to trust the hook in `/hooks`;
    7. ends with a smoke test: one spawn shows its decision line, and an agent shell does not see the key.
34. FR-039 The calibration script gains a Codex mode. It maps the labelled set to two tiers, records the resolved Jev model and exits 1 below 85%, as the default mode does. Its figures are reported as a sanity check, not as accuracy.

**Escalation instructions**

35. FR-040 Each new plugin ships an escalation skill that mirrors `plugins/model-router/SKILL.md`.
    - Escalate on three triggers: a report of BLOCKED, a failed check that the brief names, or two fix rounds without progress.
    - When steps were skipped, re-dispatch on the same tier at higher effort.
    - Otherwise go one tier up. Level 0 goes one tier up on its first failure, skipped steps included.
    - Above the top tier, raise effort.
    - The flagship model (Astra on Codex) is used only on the user's opt-in, and routing never assigns it.
    - A re-dispatch names its target explicitly, so routing leaves it alone. On omp it names a `router_*` agent and an `effort`. On Codex it names a `model` and a `reasoning_effort`.
    - The Codex skill adds one rule: after an unknown-model error, retry with an explicit `model`.

    - a run mode and a selftest mode.
39. FR-061 Each shipped harness has at least one case. A real headless client is asked to spawn one subagent for a trivial task. The case asserts these points:

    - the first spawn was routed. On Claude Code the decision line is present. On omp the rewritten agent appears in the event stream. On Codex the session files show the routed model.

### Non-Functional Requirements

1. NFR-001 Claude Code users see these changes only:
   - the brief truncation of FR-004;
   - one retry, which can mean a second request on a routed call (FR-005);
   - the line suffix of FR-006.
2. NFR-002 Routing never blocks a spawn.
   - Claude Code and Codex fail open.
   - The omp extension fails open by design (FR-027).
   - The routing deadline is 8 s, retry included, so omp's 30 s handler timeout and the 15 s Codex hook timeout are never reached.
   - A rewrite to a router agent that omp cannot resolve is caught by the setup checks and by the smoke test (FR-029). It is listed as an open risk.
3. NFR-003 Secrets:
   - The TypeSafe key goes only to the fixed endpoint, as a bearer token. It is never logged or printed, and no interview asks for it in chat.
   - On Codex, with the user's consent, the key is excluded from agent shells. The README states the exposure when the user declines.
   - The bindings read these variables and nothing else: `TYPESAFE_API_KEY` and `MODEL_ROUTER_JEV`. omp also reads its own credential store.
4. NFR-004 Privacy:
   - Every plugin folder ships a PRIVACY.md.
   - Each of them states what is sent: the brief, the role, the description and, on omp, the capped batch context. It also states that the brief is sent before the harness's approval on omp and Codex.
   - Each states the request count: up to two requests per routed call, and on omp up to two per batch item. A retried network failure may be billed twice.
   - The plugins' runtime code stores nothing on disk and keeps no routing state between calls. The setup interviews write only the configuration named in FR-029 and FR-038.
5. NFR-005 Dependencies:
   - No plugin gains a runtime dependency.
   - Development tooling stays under the existing `.npmrc` rules and CI audits.
   - The Claude Code plugin folder keeps no `package.json`.
   - The omp extension declares the minimal types it uses locally, so it needs no omp package.
6. NFR-006 Runtimes:
   - The omp extension runs inside omp.
   - The Codex hook runs unbuilt on Node 22.18 or later, or on Bun. CI also runs the Codex tests on Node 22.18.
   - Shared files use only erasable TypeScript syntax and `.ts` import specifiers.
7. NFR-007 CI:
   - `npm run check` gains the sync check, `node --test` for `shared/` and the omp and Codex tests, and the evals selftest.
   - `ci.yml` runs each of these as its own step.
   - `tsconfig` coverage extends to `shared/` and the new folders.
   - The plugin policy scan stays on the Claude Code folder, because it applies the Claude Code plugin policy.
   - A test in each new plugin pins its harness surface. Codex: the exact `hooks.json`, whose command, matcher and timeout feed the trust hash. omp: the extension registers `tool_call` only.
8. NFR-008 No artifact names the owner's accounts, plans, employer, keys, machines, local paths or installed tools. That covers `docs/gangsta/`, fixtures and the probe-derived files. The probe report itself stays outside the repository. Every diff is checked for this before commit.

## Architectural Decisions

- **One shared pure core, copied byte-identically.** The Don's principle: everything the harnesses repeat is shared, and the rest is per harness.
- **No network code in the Claude Code folder.** The policy scan reads every file under the Claude Code `hooks/` folder, and its verdict is nondeterministic.
- **The core owns the typed error and the retry rule.** Every harness then behaves the same, and the Claude Code folder holds no network helper.
- **omp effort: three `auto` agents plus the `effort` field.** omp's own `task.enableEffort` setting is the visible mode switch. The light tier never gets the lowest level.
- **Practices taken from omp:**
  - head-and-tail truncation;
  - typed errors with one retry;
  - the answering Jev model on the line.
- **Practices rejected,** because they conflict with `docs/model-choice.md` and PRIVACY.md:
  - the downward tie rule;
  - argmax reading;
  - keep-last-level fallback;
  - the keyword bypass;
  - judge fallback chains;
  - the cooldown.
- **Codex: two tiers, Astra excluded.** This is the Don's decision, following OpenAI's positioning of Luna and Sol.
- **Three catalogs and three folders.** Each harness reads only its own catalog. Otherwise Codex loads the Claude Code hook file and warns, and omp drops agent models in Claude-dialect plugins (dossier, Packaging Intel).

## Grilling Conclusions

### Key Decisions

The binding decisions are listed in `docs/gangsta/multi-harness/checkpoints/02-the-grilling.md`, section Key Decisions. This contract adds four things on top of them:
- the folder and catalog paths (FR-020, FR-030, FR-050);
- the Sequencing section;
- the G1 rules per multi-agent version;
- the per-requirement details in the Requirements section.

### Rejected Alternatives

- **Hermes Agent:** `delegate_task` has no per-task model.
- **Compiled binaries and agent-generated scripts:** the TypeScript reference runs directly.
- **Twelve omp agents with an environment switch, and per-model effort snapping:** replaced by three `auto` agents.
- **Interview-generated agents:** they go stale and come out different on each run.
- **A suffix-only Codex matcher:** it also matches MCP tools.
- **Network code in the Claude Code copy:** the policy scan reads it.
- **An environment-selected hook runtime, and an overridable endpoint:** either could redirect execution or the key.
- **Measured savings and shadow mode:** outside the Don's success criterion.
- **Approaches B (three releases) and C (Claude Code later):** the Don chose one release.

### Unresolved Objections

- **Fork routing policy for Codex v2 and for Claude Code.** Risk: MEDIUM. Mitigation: forks stay unrouted, the probe's fork runs inform the decision, and an issue tracks it.
- **Codex tier texts rest on a 21-case relabel.** Risk: MEDIUM. Mitigation: they are marked provisional, and an issue tracks an outcome-labelled set.
- **The omp extension cannot read `task.enableEffort` or `task.maxEffort`.** The line therefore shows the requested effort only. A user who turns `task.enableEffort` on by hand, outside the setup, without the cap can get `max`. That setting is outside the plugin's control. Risk: LOW. Mitigation: the setup never sets one setting without the other, the smoke test checks the cap, and the README states the residual case.
- **omp maps `med` to low on a model with only low, high and max.** Risk: LOW. Accepted.

## Out of Scope

- Hermes Agent.
- More than three tiers, or a user-chosen tier count.
- Compiled binaries and release artifacts for the hook.
- Recalibrating Claude Code tier texts beyond keeping G2.
- Measuring savings, shadow mode, and comparing quality against an unrouted baseline.
- Routing specialised omp agents or Codex roles other than `default`.
- Codex on Windows.
- Custom TypeSafe base URLs.
- Changing Claude Code's fork rule.
- Running the plugin policy scan on the omp and Codex folders.

## Open Risks

1. **The Codex v2 `message` may be opaque to hooks.** Risk: HIGH for Codex, none for the rest. Mitigation: G1 per version, and the deferral path.
2. **Calibration transfer to omp model pools and to Codex is unmeasured.** Risk: MEDIUM. Mitigation: provisional labels and a tracked issue.
3. **The policy scan is nondeterministic.** The Claude Code folder changes in step 2 and again for docs and the version in step 5, and each change reruns the scan. The omp and Codex folders get no policy scan. Risk: LOW. Mitigation: changes to the Claude Code folder are batched into those two steps.
4. **Router agents drift from omp's bundled `task` agent.** Risk: MEDIUM. Mitigation: the attribution names the source version, and the omp eval records drift (FR-061).
5. **A user who declines the Codex exclusion exposes the key to agent shells.** Risk: MEDIUM. Mitigation: the README and PRIVACY.md state it.
6. **A Codex catalog change after setup makes a slug invalid.** Routed spawns then fail with tool errors. Risk: LOW. Mitigation: the escalation skill retries with an explicit model, and the line shows the slug.
7. **omp cannot resolve a router agent after setup.** For example, the user later adds it to `task.disabledAgents`. Routed spawns then fail. Risk: LOW. Mitigation: setup checks, the smoke test and README troubleshooting.
8. **A client may not expose the decision line in machine-readable form.** That weakens FR-061 for that client. Risk: LOW. Mitigation: the case asserts routing, and the gap goes into the coverage issue.
9. **The retry can bill twice and doubles omp's request count on failures.** Risk: LOW. Mitigation: NFR-004 discloses it, and the retry is limited to one attempt.
